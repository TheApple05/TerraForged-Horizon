# Horizon integration scope

The Java 26.2 port and Horizon are separate targets. The inspected Horizon
installation pins Java Edition 26.3/protocol 777 and runs native Rust code.
Fabric/NeoForge JARs cannot be installed as native Horizon mods.

The initial implementation in [horizon/](../../horizon/README.md) is a finite
prepared terrain pipeline. It imports terrain generated by the real Java port
and reconstructs it with Horizon's registry-backed `TerrainChunk` and
`BiomeChunk` types. Full chunk generation, stored/noise biome lookups, column
material spans and LOD queries read the same snapshot. Missing coverage errors
explicitly. Other dimensions use their original pipelines.

The native bundle uses a revision-pinned cancellable HEAD injection into
`OverworldGenerator::for_world_with_settings`. Horizon commit
`9dd5c4093977c718c5c0349032fd3a5434e86afc` changes only the method's
`Result<Self, GeneratorError>` spelling to the equivalent concrete result and
documents the native injection target. This is required because the inspected
official mixin tool rejects cancellation over `Self`; an attempted OVERWRITE
also rejects the original constructor's `?`/closures. Those failed approaches
were not called successful native runtime tests. Original source checkouts are
never patched in place by the staging tools.

This integration is based on the inspected current owned main,
`da6b3c353d9bc495704f3658bdb09fade27e2679`. Earlier installed-nightly tests at
`b33bc70c` plus `7fb69700` are rehearsals; they do not substitute for validation
against the current integration pin. The current branch retains all 381 commits
between those baselines.

Biome IDs are resolved against the actual native registry. Exported classic
biome JSON must be supplied through real Horizon worldgen overrides/content
before loading its snapshot. An unknown custom biome fails; it is never
remapped to vanilla to make the probe pass. Native terrain feature algorithms
are not inferred from the presence of a biome JSON entry.

Native infinite generation remains unfinished. The bridge also does not
restore structure starts/locate, typed entities, block entities or scheduled
ticks. A generated Java world save does not prove a Horizon save round trip.
Rendered client, normal launcher install and general Horizon modpack acceptance
require separate evidence. The bridge is therefore experimental even if its
complete block/biome corpus comparison passes.

The adapter is original MIT code against Horizon's MIT API. The bundle retains
the Horizon MIT notice. No Mojang source or prepared resources are included.

The [current-main/dev18 validation](../validation/horizon-current-dev18.md)
records the exact Java producer and native source pins, complete block/biome
comparison, packaged source hashes, failures/corrections and the separate
launcher/rendering/save gates. The [Horizon integration PR](https://github.com/TheApple05/horizon/pull/1)
changes only the constructor return-type spelling and its documentation.
It merged as `21679eb68f770d3ac1c2cc1c51a535eea37787ab`; the merged tree is
identical to the tested `9dd5c409` pin. Later Java builds require their own
producer corpus and native comparison.
