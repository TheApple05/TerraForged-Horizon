# Next milestone: the complete infinite cell/tile kernel

The prepared-world bridge is a tested intermediate implementation. Infinite
native TerraForged generation is still required. The next useful unit is the
complete cell/tile pipeline for one exact default preset, exposed as a native
column sampler and checked against the actual packaged Java implementation.
It must produce new terrain at coordinates absent from any prepared snapshot.
It is not yet a replacement for the entire native chunk generator.

## Required source and dependency surface

The measured conservative inventory is generated by
`python horizon/tools/inventory_kernel.py --output docs/horizon/kernel-source-inventory.json`.
It records each source hash, nonempty line count and imports outside the
selected packages. It is a package inventory rather than a claim of minimal
method reachability. The main groups contain 58 noise, 65 cell, 16 tile and
12 preset-settings source files, plus six worldgen utilities and
`GeneratorContext`, `WorldFilters` and `WorldErosion`.

The terrain unit is the actual ordered pipeline:

1. `Heightmap.make` constructs the seeded region, terrain, continent, ocean,
   mountain and beach graphs from the preset and registered noise values.
2. `applyTerrain` sets the continent, region and terrain fields.
3. `applyRivers` applies the rivermap and volcano adjustment.
4. `applyClimate` applies river/lake/wetland adjustments, the climate regions,
   coastline changes and macro biome weirdness changes.
5. `TileGenerator.generate` evaluates the full configured tile and border.
6. `WorldFilters` applies erosion, smoothing, steepness, beach detection and
   corrections in Java order.

The default preset selects `MULTI_IMPROVED` continents; implementing only
`SimpleContinent` does not implement that preset. `GROUND` is merely the
registered sea-level/scaler constant, so porting that noise alone would not be
a terrain generator. Erosion and beach/steepness filters require neighboring
cells; independent height queries cannot stand in for complete tiles.

The Rust kernel should represent the preset and noise graphs as typed data.
Minecraft `HolderGetter`, codecs and registry bootstrapping become explicit
validated adapters, not dependencies on Mojang implementation code. Java
collections, cache/pool ownership and `CompletableFuture` scheduling become
native bounded ownership and deterministic work scheduling. Additional project
imports in the inventory (biome climate ranges, caches, pools and configuration)
must be inspected and classified before declaring the closure complete.

The existing Horizon `SeededPipeline` hook is sufficient to activate a future
native generator, but faithful chunks additionally need the custom cell/noise
density nodes, preset density router, climate/biome selection, surfaces,
carvers/aquifers, decoration and structures. The native cell kernel should
first feed the matching custom density nodes; filling stone below a height
field would discard caves and surface semantics and is not an acceptance gate.

## Java oracle and fixture contract

The developer-only oracle must run against the exact frozen production JAR,
qualified preset pack and Java25 classpath, independently of any Rust result.
Its manifest binds those SHA-256 values, the encoded preset, source registry
noise JSON and relevant source inventory. It records the original long world
seed and the Java kernel's narrowing `(int) seed` separately. Seed offsets and
increments wrap as signed32-bit Java operations, in the original construction
order.

For deterministic points, capture every public `Cell` numeric field using
`Float.floatToRawIntBits`, integral continent coordinates, erosion mask, terrain
identity and biome identity after each of terrain, rivers and climate. Do not
serialize floats through decimal JSON and compare rounded display values.
Noise vectors also bind their graph, minimum and maximum values. Terrain
identities must use stable names/IDs instead of Java object addresses.

Capture complete final tile interiors and their configured halo, not just
selected heights. Preserve world-to-tile addressing, negative right shifts,
masks and border offsets from `Size`/`Tile`. Capture stage results before and
after erosion/smoothing/required filters where the oracle can observe those
without changing production behavior. No private production field is mutated
to manufacture a fixture result.

The initial corpus should cover seed0, -1, signed32-bit endpoints, a seed with
different high32bits, and the actual acceptance seed; negative coordinates,
tile/chunk borders, continent coasts, rivers, lakes, terrain region transitions,
mountain chains and biome edges. Locations must be discovered with the Java
sampler. Repeated queries, reversed tile order and multiple native workers must
produce the same bits and stable cache ownership. Failed or partial work must
not enter the cache.

Rust operations preserve `f32` rounding and expression order; use wrapping
integer arithmetic where Java wraps and never introduce fused multiply-add or
an implicit `f64` intermediate. Java rounding, random, trigonometric and square
root semantics must be checked against raw-bit fixtures rather than assumed
equivalent to Rust convenience functions. Every mismatch must identify the
first differing stage/field/coordinate and block activation until explained.

## Acceptance sequence

1. Freeze and produce the independent Java corpus, including its exact source
   and registry inputs. Reproduce its digest in a second fresh run.
2. Match the noise/domain/curve arithmetic and seed graph, then all unfiltered
   cell stages. This is foundational work, not a completed Horizon port.
3. Match full filtered tiles and seams, cache eviction/reload, request ordering
   and parallel scheduling. Query uncaptured coordinates directly in Rust;
   forbid snapshot fallback.
4. Connect the complete cell kernel to actual native density/biome/surface
   execution and compare full chunks against new Java fixtures. Register the
   17 real biome IDs and explicitly reject unsupported nodes/resources.
5. Validate world-save reopen, native client rendering, normal launcher
   packaging and native mod combinations before claiming Horizon readiness.

Java26.2 and Horizon26.3 remain separate version targets. The successful finite
bridge corpus is a regression fixture for block/biome fidelity, not proof that
new native terrain, decoration or world-save behavior is correct.
